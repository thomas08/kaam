# Kaam — Architecture Design Document

> **Kaam** (ก้าม) — agent harness ที่รันเองได้ครบบนชิป ESP32-C5
> เขียนด้วย Rust · standalone · local-first
> สถานะ: ร่างสถาปัตยกรรม (pre-implementation) · แก้ไขล่าสุด 2026-08-02

---

## 0. สรุปสำหรับคนรีบ

Kaam คือ AI agent harness ที่รันบน microcontroller ตัวเดียวโดยไม่ต้องพึ่งเครื่องอื่น
รับคำสั่งผ่าน Telegram, เรียก LLM ผ่านคลาวด์, เรียก tool, จำเรื่องข้ามการรีบูตได้,
และตั้งงานประจำเองได้ ทุกอย่างเก็บเป็นไฟล์ Markdown ในแฟลชของมันเอง

หลักการออกแบบที่กำหนดทุกอย่างหลังจากนี้มี 4 ข้อ:

1. **Stream ทุกอย่าง** — ไม่มีจุดไหนที่ buffer ทั้ง request หรือทั้ง response ไว้ใน RAM
2. **Sans-IO core** — logic ทั้งหมดไม่รู้จัก network/filesystem จริง ทดสอบบนพีซีได้
3. **ทุกอย่างเป็นไฟล์** — state คือ Markdown/JSONL ที่มนุษย์อ่านและแก้ได้
4. **งบประมาณชัดเจน** — RAM, token, เวลา, เงิน ทุกอย่างมี hard cap ที่บังคับใช้ในโค้ด

## 1. เป้าหมายและขอบเขต

### 1.1 เป้าหมาย

| # | เป้าหมาย | วิธีวัดว่าสำเร็จ |
|---|---|---|
| G1 | ทำงานเองครบวงจร ไม่พึ่งเครื่องหลัก | ถอดพีซีออกแล้วยังใช้งานได้เต็มรูปแบบ |
| G2 | อยู่ได้นานโดยไม่ต้องรีบูต | uptime ≥ 30 วันภายใต้การใช้งานปกติ |
| G3 | ข้อมูลอยู่กับผู้ใช้ | ไม่มี telemetry, ข้อมูลออกนอกเครื่องเฉพาะไป LLM provider ที่ผู้ใช้เลือก |
| G4 | อ่านและแก้ state ได้ด้วยมือ | ดึงแฟลชมา mount แล้วแก้ไฟล์ได้โดยไม่ต้องใช้เครื่องมือพิเศษ |
| G5 | ต่อยอดได้โดยไม่ต้อง reflash | เพิ่ม skill / MCP server ได้ผ่านการเขียนไฟล์ |
| G6 | ล้มแล้วฟื้นเอง | ตัดไฟกลางเทิร์นแล้วบูตกลับมาไม่มี state เสียหาย |

### 1.2 นอกขอบเขต (ตัดทิ้งอย่างตั้งใจ)

- GUI ทุกชนิด, code editor, การ render เอกสาร
- Agent teams / git worktree — ต้องมี process จริงและ git ซึ่งไม่มีบน MCU
- อ่าน/สร้าง PDF, DOCX, XLSX
- รัน LLM ในเครื่อง (inference บนชิปนี้เป็นไปไม่ได้)
- Vector embedding / semantic search — ใช้ grep + read แทน ตามแนวทาง LLM-wiki
- Multi-user — หนึ่งเครื่องต่อหนึ่งเจ้าของ

### 1.3 ข้อสมมติ

- มี WiFi ที่ต่ออินเทอร์เน็ตได้ (ยอมให้หลุดชั่วคราวได้ ต้องฟื้นเอง)
- มี API key ของ LLM provider อย่างน้อยหนึ่งเจ้า
- เจ้าของเครื่องเป็นคนเดียวและเชื่อถือได้
- จ่ายไฟจาก USB ตลอดเวลา (ไม่ใช่โจทย์แบตเตอรี่)

## 2. ฮาร์ดแวร์เป้าหมาย

### 2.1 ตัวหลัก: ESP32-C5-WROOM-1-N16R8

| ทรัพยากร | ขนาด | หมายเหตุ |
|---|---|---|
| CPU | RISC-V 32-bit **single core** @ 240 MHz | + LP core 40 MHz (ใช้ไม่ได้กับงาน agent) |
| SRAM ภายใน | 384 KB | คอขวดตัวจริง |
| PSRAM | 8 MB (Quad SPI @ 80 MHz) | ผ่าน cache ช้ากว่า SRAM มาก |
| Flash | 16 MB | |
| WiFi | 802.11ax dual-band 2.4/5 GHz | 5 GHz คือข้อได้เปรียบจริงในบ้านที่ย่าน 2.4 แน่น |

### 2.2 ผลที่ตามมาจากการเป็น single core

นี่คือความแตกต่างสำคัญที่สุดจาก MimiClaw ซึ่งแยก network I/O กับ agent loop คนละคอร์
Kaam ทำแบบนั้นไม่ได้ จึงต้องยึดกฎ:

- **ห้าม busy-wait ทุกกรณี** — ต้อง block บน queue/semaphore เท่านั้น
- **TLS handshake คือ CPU spike** ที่จะทำให้ task อื่นหยุดหายใจ ต้องนับไว้ในงบเวลา
- **งานยาวต้องหั่นเป็นชิ้น** — เช่นการสแกน skill ทั้งโฟลเดอร์ ต้อง yield ระหว่างไฟล์
- ตั้ง `CONFIG_FREERTOS_HZ=1000` เพื่อให้ preemption ละเอียดขึ้น

### 2.3 ทางเลือกที่พิจารณาแล้วไม่เอา

| ชิป | เหตุผลที่ตัด |
|---|---|
| ESP32-S3 | ได้ dual core แต่เป็น Xtensa ต้องใช้ toolchain แยก (espup) ซึ่งขัดกับเหตุผลที่เลือก RISC-V |
| ESP32-C6 | ไม่รองรับ PSRAM — จบตั้งแต่ต้น |
| ESP32-C3 | ไม่มี PSRAM, SRAM 400 KB |
| ESP32-P4 | แรงกว่ามากแต่ไม่มีวิทยุ ต้องพ่วง C6 ผ่าน ESP-Hosted ซึ่งยังไม่นิ่ง — เก็บไว้เป็น Kaam Pro รุ่นมีจอ |

## 3. งบประมาณหน่วยความจำ

เอกสารนี้ถือว่างบ RAM คือสัญญา ไม่ใช่การประมาณ — ทุก milestone ต้องวัดจริงเทียบกับตาราง

### 3.1 SRAM ภายใน 384 KB

| ผู้ใช้ | ประมาณการ | หมายเหตุ |
|---|---|---|
| WiFi driver + buffer | 60–70 KB | ต้องอยู่ใน internal เท่านั้น |
| lwIP | 25–30 KB | ปรับ PBUF/TCP window ลงได้ |
| FreeRTOS + task stacks | 40 KB | 5 task ตามข้อ 5.2 |
| mbedTLS session ที่ active | 30–45 KB/เส้น | ดูข้อ 3.3 |
| ESP-IDF ระบบอื่น | 30 KB | |
| Rust runtime + static | 20 KB | |
| **เหลือเป็น headroom** | **~100 KB** | เป้าหมายขั้นต่ำ ห้ามต่ำกว่า 60 KB ขณะ idle |

**เกณฑ์เตือน:** ถ้า `esp_get_free_internal_heap_size()` < 45 KB ให้ปฏิเสธการเริ่มเทิร์นใหม่
และสั่ง compaction ก่อน — ดูข้อ 9.4

### 3.2 PSRAM 8 MB

| ผู้ใช้ | จอง | หมายเหตุ |
|---|---|---|
| Working context buffer | 512 KB | ข้อความที่จะประกอบเป็น prompt |
| Streaming scratch | 256 KB | SSE line buffer + JSON partial |
| Tool result staging | 512 KB | ผลลัพธ์ tool ก่อนตัดทอน |
| Skill/KMS cache | 256 KB | เนื้อ skill ที่ถูก trigger |
| Task stack ที่ย้ายลง PSRAM | 64 KB | `xTaskCreateStatic` เท่านั้น |
| ว่าง | ~6.4 MB | เผื่ออนาคต — ไม่ต้องรีบใช้ |

ตั้ง `CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL=8192` เพื่อให้ก้อนใหญ่กว่า 8 KB ตกไป PSRAM อัตโนมัติ

### 3.3 เรื่อง TLS ที่ต้องรู้ก่อนเขียนบรรทัดแรก

Kaam ต้องเปิด TLS ไปสองปลายทางพร้อมกัน (Telegram + LLM) ซึ่งเป็นจุดที่ heap แตกบ่อยที่สุด

มาตรการที่ต้องมีตั้งแต่วันแรก:

- `CONFIG_MBEDTLS_DYNAMIC_BUFFER=y` — คืน buffer หลัง handshake เสร็จ ลดจาก ~45 KB เหลือ ~8 KB ต่อเส้น
- `MBEDTLS_SSL_IN_CONTENT_LEN=16384` / `OUT_CONTENT_LEN=4096` — ขาเข้าต้องใหญ่เพราะ record ของ provider ใหญ่ ขาออกเล็กได้
- **TLS session ticket reuse** — เก็บ ticket ใน NVS ต่อ host ประหยัด handshake ~1.5 วินาทีและ CPU spike
- ใช้ certificate bundle ของ ESP-IDF ไม่ต้องฝัง cert เอง
- **ห้ามเปิดสองเส้นพร้อมกันตอน handshake** — มี `tls_gate` semaphore นับได้ 1 ตัว กั้นเฉพาะช่วง handshake แล้วปล่อย

## 4. โครงสร้าง crate

จุดสำคัญคือแยก **logic ที่ทดสอบบนพีซีได้** ออกจาก **โค้ดที่ต้องรันบนชิป** ให้เด็ดขาด
เป้าหมายคือ 85–90% ของ logic ทดสอบด้วย `cargo test` บน x86 ได้โดยไม่ต้องเสียบบอร์ด

```
kaam/
├── crates/
│   ├── kaam-types/      # ชนิดข้อมูลกลาง ไม่มี dependency ฝั่ง IO
│   ├── kaam-provider/   # sans-io: byte in → event out
│   ├── kaam-agent/      # ReAct state machine + context manager
│   ├── kaam-tools/      # tool registry + built-in tools (ผ่าน trait)
│   ├── kaam-mcp/        # MCP client (HTTP+SSE) แบบ sans-io
│   ├── kaam-skills/     # parser + trigger matcher ของ SKILL.md
│   ├── kaam-store/      # trait storage + impl in-memory สำหรับ test
│   └── kaam-chat/       # Telegram protocol แบบ sans-io
└── firmware/
    └── kaam-fw/         # binary เดียว: ESP-IDF glue, task, driver จริง
```

### 4.1 ทำไมต้อง sans-io

`kaam-provider` ไม่รู้จัก socket มันมีหน้าตาแบบนี้ (แนวคิด ไม่ใช่โค้ดจริง):

```
feed(&mut self, chunk: &[u8]) -> impl Iterator<Item = ProviderEvent>
next_request(&mut self) -> Option<Vec<HttpChunk>>
```

ผลที่ได้:

- ทดสอบ streaming parser ด้วยไฟล์ SSE ที่บันทึกไว้ ไม่ต้องมีเน็ต
- ทดสอบกรณี chunk ขาดกลางคัน / ขาดครึ่ง UTF-8 / SSE event ครึ่งบรรทัด ได้ครบ
- fuzz test ได้บน host
- เปลี่ยน HTTP client ข้างล่างโดยไม่แตะ logic

ข้อแลกเปลี่ยน: โค้ดอ่านยากขึ้นและต้องจัดการ state ของ parser เอง — คุ้มค่า เพราะ debug บนชิปแพงกว่ามาก

### 4.2 กฎ dependency

- `kaam-types` ห้าม depend อะไรนอกจาก `serde` และ `heapless`
- crate ใน `crates/` ห้าม depend `esp-idf-*` ทุกตัว **โดยเด็ดขาด** — บังคับด้วย CI ที่รัน `cargo test --target x86_64` 
- `kaam-fw` เป็นที่เดียวที่รู้จักฮาร์ดแวร์

## 5. โมเดลการทำงานพร้อมกัน

### 5.1 ภาพรวมการไหลของข้อมูล

```
Telegram ──┐
           ├──▶ inbox_q ──▶ [agent task] ──▶ outbox_q ──▶ Telegram
WebSocket ─┘                    │  ▲
                                │  │
Scheduler ──────────────────────┘  │
                                   │
                         tool call │ result
                                   ▼
                          [tool dispatcher]
                          ├─ fs / memory / http
                          └─ mcp client
```

### 5.2 ตาราง task

| Task | Priority | Stack | ที่อยู่ | หน้าที่ | Block ตรงไหน |
|---|---|---|---|---|---|
| `net_in` | 6 | 8 KB | internal | long-poll Telegram, รับ WS | socket recv |
| `agent` | 5 | 12 KB | PSRAM | รัน turn ทีละอัน | `inbox_q` |
| `net_out` | 6 | 6 KB | internal | ส่งข้อความออก | `outbox_q` |
| `sched` | 3 | 4 KB | internal | tick ทุก 1 วิ ตรวจ cron | `vTaskDelay` |
| `sys` | 2 | 4 KB | internal | watchdog, memory monitor, OTA check | `vTaskDelay` |
| `audio_in` | 7 | 6 KB | internal | อ่าน I2S ขณะกดปุ่ม (ถ้ามีเสียง) | I2S DMA |
| `audio_out` | 7 | 6 KB | internal | ป้อน ring buffer เข้า I2S (ถ้ามีเสียง) | ring buffer |

> Task เสียงมี priority สูงสุดในกลุ่มของเรา เพราะเสียงสะดุดสังเกตได้ทันทีต่างจากข้อความช้าไปครึ่งวินาที
> ทั้งคู่คอมไพล์เข้ามาเฉพาะเมื่อเปิด feature flag `voice` — ดูข้อ 19

> Task ของ ESP-IDF เอง (WiFi prio 23, lwIP prio 18) อยู่สูงกว่าทั้งหมด — ถือเป็นเรื่องปกติ

### 5.3 หลักการที่ห้ามละเมิด

- **มีเทิร์นที่กำลังทำงานได้ทีละหนึ่ง** — ข้อความที่เข้ามาระหว่างนั้นเข้าคิว ไม่ตัดคิว
  (single core, การทำสองเทิร์นพร้อมกันไม่ได้เร็วขึ้นแต่จะทำให้ RAM แตก)
- `inbox_q` ลึก 8 ถ้าเต็มให้ตอบผู้ใช้ว่ากำลังยุ่ง อย่าเงียบ
- `net_in` กับ `net_out` แยกกันเพื่อให้ส่งข้อความ "กำลังคิดอยู่" ได้ระหว่าง agent ทำงาน
- ทุก task register กับ Task Watchdog Timer ยกเว้น `agent` (ซึ่งมี timeout ของตัวเองที่ยาวกว่า)

## 6. เลย์เอาต์แฟลช 16 MB

```
# name       type  subtype   offset     size
nvs          data  nvs       0x9000     0x6000     # 24 KB  config ที่ไม่ใช่ความลับ
nvs_keys     data  nvs_keys  0xF000     0x1000     #  4 KB  key สำหรับ NVS encryption
otadata      data  ota       0x10000    0x2000     #  8 KB
phy_init     data  phy       0x12000    0x1000     #  4 KB
ota_0        app   ota_0     0x20000    0x380000   # 3.5 MB
ota_1        app   ota_1     0x3A0000   0x380000   # 3.5 MB
coredump     data  coredump  0x720000   0x10000    # 64 KB
storage      data  littlefs  0x730000   0x8C0000   # ~8.75 MB
```

**เหตุผลที่ให้ app partition 3.5 MB:** binary ของ Rust + ESP-IDF ที่มี TLS มักอยู่ราว 1.5–2.5 MB
ซึ่งใหญ่กว่า C ของ MimiClaw ชัดเจน — นี่คือราคาที่จ่ายเพื่อได้ Rust
ให้เผื่อไว้ 40% เพราะการขยาย partition หลังปล่อยของแล้วทำไม่ได้โดยไม่ล้าง OTA

**ตั้งงบไว้เลย:** ถ้า binary โตเกิน 2.8 MB ให้ถือเป็น build failure ไม่ใช่แค่คำเตือน

เลือก **LittleFS ไม่ใช่ SPIFFS** เพราะทนไฟดับ (copy-on-write) มีโฟลเดอร์จริง และ wear-leveling ดีกว่า

### 7.1 กฎการเขียนไฟล์

- **เขียนแบบ atomic เสมอ**: เขียน `.tmp` → `fsync` → `rename` ทับ
  (LittleFS รับประกันว่า rename เป็น atomic)
- **session เป็น JSONL append-only** — ไฟดับกลางทางเสียแค่บรรทัดสุดท้าย
  ตอนบูตให้อ่านแล้วทิ้งบรรทัดที่ parse ไม่ผ่านท้ายไฟล์
- ห้ามเขียนไฟล์เดียวถี่กว่า 1 ครั้ง/วินาที (ยืดอายุแฟลช)
- ทุกไฟล์ที่ agent เขียนต้องผ่าน path canonicalization ที่จำกัดอยู่ใต้ `/kaam/`

## 8. Provider layer

### 8.1 สัญญาที่ต้องมีเหมือนกันทุกเจ้า

รองรับ Anthropic และ OpenAI ก่อน สลับได้ตอนรันไทม์ผ่าน `settings.json` หรือคำสั่ง

Provider แต่ละตัวต้องแปลงเป็น event ชุดกลางนี้:

```
TextDelta(&str)
ThinkingDelta(&str)
ToolCallStart { id, name }
ToolCallArgDelta(&str)
ToolCallEnd
TurnEnd { stop_reason, usage }
Error { retryable: bool, .. }
```

### 8.2 ทำไม request ก็ต้อง stream

จุดนี้มักถูกมองข้าม — คนมักคิดถึงแค่ response

conversation ที่ยาว 60 KB เมื่อ serialize เป็น JSON แล้วต้อง escape จะกลายเป็นก้อน ~80 KB
ถ้าสร้างทั้งก้อนใน RAM ก่อนส่ง เท่ากับต้องมี 80 KB ต่อเนื่องกันใน PSRAM
ซึ่งกับ heap ที่ fragment แล้วมีโอกาสล้มสูง

ทางแก้: ใช้ **HTTP chunked transfer encoding** แล้วสร้าง JSON ทีละ message
เขียนลง socket ไปเรื่อย ๆ — RAM ที่ใช้จริงคือขนาดของ message ที่ใหญ่ที่สุดเพียงอันเดียว

### 8.3 การจัดการข้อผิดพลาด

| กรณี | การตอบสนอง |
|---|---|
| HTTP 429 | อ่าน `retry-after` แล้ว backoff แบบ exponential + jitter สูงสุด 5 ครั้ง |
| HTTP 5xx | backoff เหมือนกัน |
| HTTP 401/403 | หยุด ไม่ retry แจ้งผู้ใช้ว่า key มีปัญหา |
| context ยาวเกิน | compaction ทันทีแล้วลองใหม่หนึ่งครั้ง ดูข้อ 9.4 |
| socket ขาดกลาง stream | ทิ้งเทิร์น แจ้งผู้ใช้ ไม่ retry อัตโนมัติ (อาจเสียเงินซ้ำ) |

## 9. Agent core

### 9.1 State machine ของหนึ่งเทิร์น

```
Idle
 └─▶ Assemble      ประกอบ prompt ตามข้อ 9.3
      └─▶ Stream   ยิง request, อ่าน event
           ├─▶ Emit        ส่ง TextDelta ออก outbox (ทยอยส่ง)
           ├─▶ ToolWait    ถ้ามี tool call
           │    └─▶ Dispatch → ผลลัพธ์เข้า context → กลับไป Stream
           └─▶ Finalize    เขียน session, อัปเดต usage
                └─▶ Idle
```

### 9.2 งบประมาณของเทิร์น (บังคับใช้ในโค้ด)

| งบ | ค่าเริ่มต้น | เมื่อเกิน |
|---|---|---|
| จำนวนรอบ tool | 12 | หยุดแล้วรายงานสิ่งที่ทำไปแล้ว |
| เวลาทั้งเทิร์น | 180 วิ | ยกเลิก แจ้งผู้ใช้ |
| token ต่อเทิร์น | 60k | ยกเลิกก่อนยิง |
| token ต่อวัน | ตั้งได้ | ปฏิเสธเทิร์นใหม่ แจ้งเตือน |
| ขนาดผล tool หนึ่งอัน | 8 KB | ตัดแล้วใส่หมายเหตุว่าถูกตัด |

งบ token ต่อวันคือกันไม่ให้ loop ที่พังกินเงินข้ามคืน — ต้องมีตั้งแต่ M2 ไม่ใช่ทีหลัง

### 9.3 การประกอบ prompt

ลำดับชั้น จากคงที่ไปหาแปรผัน (เรียงแบบนี้เพื่อให้ provider cache prefix ได้):

1. SOUL.md — บุคลิก
2. AGENTS.md — instruction
3. รายการ tool (built-in + MCP ที่ discover ได้)
4. หัวข้อ skill ทั้งหมด (เฉพาะ frontmatter บรรทัดเดียวต่ออัน)
5. USER.md + MEMORY.md ที่กลั่นแล้ว
6. เนื้อ skill ที่ถูก trigger ในเทิร์นนี้
7. สรุปย้อนหลัง (ถ้ามี)
8. ข้อความ N เทิร์นล่าสุด

### 9.4 การจัดการ context และ compaction

นี่คือกลไกที่ทำให้ G2 (อยู่ได้นาน) เป็นจริง — ถ้าไม่มี เครื่องจะพังภายในไม่กี่วัน

**ตัวกระตุ้น** (อย่างใดอย่างหนึ่ง):
- ประมาณการ token ของ context > 70% ของเพดานที่ตั้งไว้
- จำนวนข้อความ > 40
- free internal heap < 45 KB

**ขั้นตอน:**
1. หยุดรับเทิร์นใหม่
2. เอาข้อความเก่าครึ่งแรกยิงเข้า LLM ด้วย prompt สรุปเฉพาะทาง
3. ผลลัพธ์เขียนลง `memory/journal/<วันที่>.md` (ต่อท้าย)
4. ข้อเท็จจริงถาวรที่ได้ merge เข้า `MEMORY.md`
5. แทนข้อความครึ่งแรกใน context ด้วยบล็อกสรุปก้อนเดียว
6. เขียน `sessions/current.jsonl` ใหม่ทั้งไฟล์แบบ atomic

**เหตุผลที่แยก journal กับ MEMORY.md:** journal คือ audit trail ที่ต่อท้ายอย่างเดียว
ส่วน MEMORY.md ถูกเขียนทับได้ — ถ้าการกลั่นทำข้อมูลหาย ยังย้อนไปดู journal ได้เสมอ

## 10. Tool layer

### 10.1 Built-in tools

| Tool | ทำอะไร | ระดับความเสี่ยง |
|---|---|---|
| `read_file` / `list_dir` | อ่านใต้ `/kaam/` | ปลอดภัย |
| `write_file` / `edit_file` | เขียนใต้ `/kaam/` | ต้องยืนยัน (ตั้งค่าได้) |
| `remember` | เพิ่มข้อเท็จจริงลง MEMORY.md | ปลอดภัย |
| `http_get` | ดึง URL (มี allowlist) | ต้องยืนยัน |
| `web_search` | ผ่าน search API ที่ผู้ใช้ตั้ง key | ปลอดภัย |
| `schedule_add` / `schedule_list` / `schedule_remove` | จัดการ cron | ต้องยืนยัน |
| `gpio_read` / `gpio_write` | คุมขาสัญญาณ | ต้องยืนยัน |
| `sys_status` | heap, uptime, WiFi RSSI, token ที่ใช้วันนี้ | ปลอดภัย |
| `propose_soul_edit` | เสนอแก้บุคลิกตัวเอง | **ต้องอนุมัติเสมอ** ปิดไม่ได้ ดูข้อ 18 |
| `speak` | พูดข้อความออกลำโพง | ปลอดภัย (เฉพาะบอร์ดที่มีเสียง) |

> `write_file` ตั้งเป็น `deny` ถาวรกับทุก path ใต้ `identity/` และ `config/` —
> ทางเดียวที่แตะ `SOUL.md` ได้คือผ่าน `propose_soul_edit`

### 10.2 MCP

- รองรับ **HTTP + SSE เท่านั้น** — stdio ทำไม่ได้เพราะไม่มี process ให้ spawn
- discovery ตอนบูตแล้ว cache รายการ tool ลง `/kaam/config/mcp-cache.json`
  (จะได้ไม่ต้อง handshake ใหม่ทุกครั้ง)
- ตั้งชื่อแบบ namespace: `mcp__<server>__<tool>` กันชนกับ built-in
- **timeout ต่อ server 15 วินาที** — server ที่ตายห้ามทำให้ทั้งเครื่องค้าง
- server ที่ล้ม 3 ครั้งติดให้ปิดชั่วคราว 10 นาที (circuit breaker)

### 10.3 นโยบายการอนุญาต

ทุก tool มีสถานะหนึ่งใน `allow` / `confirm` / `deny` ตั้งใน `settings.json`
สถานะ `confirm` ทำให้ Kaam ส่งข้อความถามใน Telegram พร้อมปุ่ม แล้วรอไม่เกิน 5 นาที
ไม่ตอบถือว่าปฏิเสธ

## 11. Skills

รูปแบบเดียวกับมาตรฐาน `SKILL.md`:

```markdown
---
name: morning-brief
description: สรุปข่าวและตารางงานตอนเช้า ใช้เมื่อผู้ใช้ขอบรีฟหรือถามว่าวันนี้มีอะไร
---
(เนื้อหา — โหลดเมื่อถูก trigger เท่านั้น)
```

**การจัดการหน่วยความจำ** คือหัวใจ: ตอนบูตอ่านเฉพาะ frontmatter ของทุก skill
เก็บไว้ใน RAM เป็นบรรทัดสั้น ๆ (~100 ไบต์/อัน) — มี 50 skill ก็ยังกินแค่ 5 KB
ส่วนเนื้อหาเต็มโหลดจากแฟลชเฉพาะตอน LLM ตัดสินใจใช้

การ trigger ให้ LLM เป็นคนตัดสินจาก description ไม่ต้องมี keyword matcher ในโค้ด —
วิธีนี้ง่ายกว่าและแม่นกว่าการทำ heuristic เอง

## 12. Scheduler

- นิพจน์แบบ cron 5 ช่อง + รูปแบบ `@every 30m` แบบง่าย
- เก็บใน `settings.json` ไม่ใช่ RAM — รอดการรีบูต
- `sched` tick ทุก 1 วินาที เทียบกับเวลาจาก SNTP
- งานที่ถึงเวลาถูกโยนเข้า `inbox_q` เหมือนข้อความจากผู้ใช้ทุกประการ
  (ทำให้ code path เดียวกัน ไม่ต้องมี logic แยก)
- **ถ้าพลาดรอบเพราะเครื่องดับ ไม่ต้องรันย้อนหลัง** — ข้ามไปรอบถัดไป
- งานที่รันเกิน 3 นาทีถูกฆ่าและบันทึกลง log

## 13. ความปลอดภัย

### 13.1 โมเดลภัยคุกคาม

| ภัย | มาตรการ |
|---|---|
| คนอื่นทักบอทใน Telegram | **allowlist `chat_id`** — ข้อความจาก id อื่นถูกทิ้งเงียบ ๆ ไม่ตอบแม้แต่ error |
| ขโมยบอร์ดไปอ่าน key | NVS encryption + flash encryption + secure boot v2 |
| prompt injection จากเนื้อหาเว็บ | ผล tool ถูกห่อด้วยตัวคั่นชัดเจนและมีคำสั่งกำกับว่าเป็นข้อมูล ไม่ใช่คำสั่ง |
| agent เขียนไฟล์นอกขอบเขต | canonicalize path แล้วตรวจ prefix ทุกครั้ง ปฏิเสธ `..` และ symlink |
| ค่า API พุ่ง | เพดาน token ต่อวัน + จำนวนรอบ tool |
| MCP server ที่ไม่น่าไว้ใจ | timeout + circuit breaker + tool policy เหมือนกันหมด |
| **agent เขียนตัวเองออกจากข้อจำกัด** | บล็อก `kaam:immutable` ตรวจแบบ byte-for-byte + `settings.json` แก้ได้ทาง serial เท่านั้น ดูข้อ 18 |
| **บุคลิกเลื่อนไหลทีละนิดจนคุมไม่ได้** | จำกัด 1 ครั้ง/วัน + แสดงระยะห่างสะสมจาก baseline ทุกครั้งที่ขออนุมัติ |
| ไมค์เปิดค้างโดยผู้ใช้ไม่รู้ตัว | LED บอกสถานะที่ขับจากฮาร์ดแวร์เดียวกับที่เปิดไมค์ + มีโหมด push-to-talk ล้วนให้เลือก |

### 13.2 การจัดการความลับ

- API key อยู่ใน NVS ที่เข้ารหัส **ไม่ใช่ในซอร์ส ไม่ใช่ในไฟล์ header**
  (จุดนี้ต่างจาก MimiClaw ที่ใส่ใน `mimi_secrets.h` ซึ่งหลุดเข้า git ได้ง่าย)
- ตั้งค่าครั้งแรกผ่าน serial console หรือหน้า provisioning ชั่วคราว
- **ห้าม key ปรากฏใน log** — มี redaction layer ที่ตัวเขียน log
- key ห้ามเข้าไปอยู่ใน context ที่ส่งให้ LLM ไม่ว่ากรณีใด

## 14. ความทนทานและการฟื้นตัว

| สถานการณ์ | พฤติกรรมที่ต้องการ |
|---|---|
| WiFi หลุด | backoff แบบ exponential + jitter, ยังรับ cron ได้แต่เข้าคิวไว้ |
| ไฟดับกลางเทิร์น | บูตมาแล้ว session อ่านได้ ทิ้งบรรทัดท้ายที่เสีย |
| Heap ใกล้หมด | ปฏิเสธเทิร์นใหม่ + compaction + แจ้งผู้ใช้ |
| Task ค้าง | TWDT รีบูต แล้วบันทึกเหตุลง coredump |
| OTA ได้เฟิร์มแวร์เสีย | ต้องผ่าน health check (WiFi ต่อได้ + ตอบ ping ใน 60 วิ) จึง `mark_app_valid` ไม่งั้น rollback อัตโนมัติ |
| แฟลชเต็ม | ลบ session archive เก่าสุดก่อน แล้วค่อยเตือน |
| เวลาเพี้ยน | ถ้า SNTP ไม่สำเร็จ ปิด scheduler ไว้ก่อน (cron ที่เวลาผิดอันตรายกว่าไม่รัน) |

### 14.1 การสังเกตการณ์

- log เป็น ring buffer 256 KB ใน LittleFS อ่านผ่านคำสั่ง `/logs` ใน Telegram
- คำสั่ง `/status` คืน uptime, free heap ทั้งสองชนิด, RSSI, token วันนี้, จำนวน MCP ที่ต่ออยู่
- นับ high-water mark ของ stack ทุก task รายงานใน `/status`

## 15. ลำดับการพัฒนา

| Milestone | เนื้อหา | เกณฑ์ผ่าน |
|---|---|---|
| **M0** | โครง repo, CI, `cargo test` บน host ผ่าน, blink บนบอร์ด | CI เขียว, flash ได้ |
| **M1** | WiFi + SNTP + TLS + Telegram long-poll | echo bot อยู่ได้ 24 ชม. โดย heap ไม่ลด |
| **M2** | Anthropic streaming + งบ token | คุยได้ ตอบทยอยออกมา มีเพดานรายวันทำงาน |
| **M3** | LittleFS + session + SOUL/USER/MEMORY | จำข้ามรีบูตได้ |
| **M4** | Tool loop + built-in tools + นโยบายอนุญาต | เรียก tool ต่อกัน 3 ชั้นสำเร็จ |
| **M5** | Compaction + journal | คุย 200 เทิร์นติดกันโดยไม่ล้ม |
| **M6** | Skills + OpenAI provider | สลับ provider ได้ตอนรันไทม์ |
| **M7** | MCP client | ต่อ MCP server จริงได้หนึ่งเจ้า |
| **M8** | Scheduler + OTA + secure boot | อัปเดตข้ามเน็ตแล้ว rollback ได้จริง |
| **M9** | `propose_soul_edit` + history + `/soul` | เสนอแก้ อนุมัติ ย้อนกลับ ครบวง และ immutable block กันได้จริง |
| **M10** | เสียงแบบ push-to-talk เต็มรูปแบบ (ปุ่ม + STT + TTS streaming + LED) | กดปุ่มพูดแล้วได้ยินคำตอบใน 3 วินาที และแตะหยุดได้ทันที |

**M1 กับ M2 จะกินเวลามากกว่าที่คิด 2–3 เท่า** เพราะปัญหา heap และ TLS ทั้งหมดจะโผล่ตรงนี้
ถ้าผ่านสองด่านนี้ได้ ที่เหลือเป็นงานเชิงตรรกะซึ่งทดสอบบนพีซีได้เกือบหมด

## 16. ความเสี่ยงที่ยังเปิดอยู่

| ความเสี่ยง | ระดับ | แผนสำรอง |
|---|---|---|
| `esp-idf-hal` รองรับ C5 ยังไม่นิ่ง (ชิปใหม่) | **สูง** | ทดสอบ M1 ให้จบก่อนลงแรงส่วนอื่น ถ้าติดจริงถอยไป C6 + จำกัด context หรือยอมกลับไป S3 |

| PSRAM fragmentation หลังรันนาน | กลาง | ใช้ arena allocator สำหรับ buffer ของเทิร์น รีเซ็ตทุกเทิร์น |
| ค่า API ในการทดสอบ | ต่ำ | ทำ mock provider ที่เล่น SSE จากไฟล์ ใช้ตลอด M3–M7 |

| เสียงสะดุดตอน TLS handshake บนคอร์เดียว | กลาง | ring buffer 128 KB + ใช้ session ticket reuse ลด handshake |
| ค่า API พุ่งจากการใช้เสียง | กลาง | เพดาน token รายวันแยกสำหรับ voice turn |

## 17. บันทึกการตัดสินใจ (ADR ย่อ)

| # | ประเด็น | ข้อสรุป | เหตุผล |
|---|---|---|---|
| D1 | การตั้งค่าครั้งแรก | **Serial console เท่านั้น** | ไม่มี SoftAP = ไม่มีหน้าต่างที่เปิดให้คนแปลกหน้าตอนบูตครั้งแรก แลกความสะดวกกับพื้นที่โจมตีที่เล็กลง |
| D2 | แก้ `SOUL.md` | **แก้ได้ แต่ต้องมีคนอนุมัติ** | ดูข้อ 18 — ต้องมีกลไกครบชุด ไม่ใช่แค่เปิด write permission |
| D3 | Session archive | เก็บ 10 อันแล้วลบวน | ตามแนวทาง `/dream` — แฟลช 8.75 MB รองรับสบาย |
| D4 | เสียง | **รองรับ แบบ push-to-talk เท่านั้น** ตั้งแต่ M10 | ดูข้อ 19 — ปุ่มแก้ปัญหาที่ไม่มี AEC ได้ตรงกว่า และคืน SRAM มา 40 KB |
| D6 | Wake word | **ไม่มี** | บนชิปที่ไม่มี AEC จะได้ประสบการณ์ครึ่ง ๆ กลาง ๆ ไม่คุ้มกับ RAM และความซับซ้อนที่จ่ายไป |
| D5 | ใบอนุญาต | Apache-2.0 / MIT dual | ธรรมเนียมของโลก Rust + ได้ patent grant |

## 18. การวิวัฒน์ของ SOUL.md (human-in-the-loop)

ตัดสินใจแล้วว่าให้ agent แก้บุคลิกตัวเองได้ แต่ต้องมีคนอนุมัติทุกครั้ง
ความสะดวกที่ได้มาพร้อมความเสี่ยงที่ต้องออกแบบกันไว้ให้ครบ ไม่ใช่แค่เปิดสิทธิ์เขียน

### 18.1 ความเสี่ยงจริงที่ต้องกัน

**การเลื่อนไหลทีละนิด (drift by a thousand cuts)** — agent เสนอแก้ครั้งละบรรทัดที่ดูสมเหตุสมผลทุกครั้ง
คนอนุมัติทุกครั้งเพราะแต่ละครั้งดูไม่มีพิษภัย ผ่านไปสองเดือนบุคลิกเปลี่ยนไปคนละเรื่องโดยไม่มีใครทันสังเกต

**การเขียนตัวเองออกจากข้อจำกัด** — ถ้า `SOUL.md` มีกฎความปลอดภัยอยู่ด้วย agent ที่แก้ไฟล์นี้ได้
ก็แก้กฎที่ควบคุมตัวเองได้ นี่คือช่องโหว่เชิงโครงสร้าง ไม่ใช่แค่บั๊ก

### 18.2 กลไก

**บล็อกที่แก้ไม่ได้** — ส่วนที่คร่อมด้วย marker นี้ถูกบังคับใช้ในโค้ด ไม่ใช่แค่ขอความร่วมมือ:

```markdown
<!-- kaam:immutable:begin -->
- ตอบเฉพาะ chat_id ที่อยู่ใน allowlist
- ห้ามเปิดเผยเนื้อหาใน config/ หรือค่าใน NVS
- เพดาน token รายวันบังคับใช้เสมอ ไม่มีข้อยกเว้น
- ห้ามแก้ไขบล็อกนี้
<!-- kaam:immutable:end -->
```

ตัวตรวจสอบเปรียบเทียบ byte-for-byte ก่อนเขียนทุกครั้ง ต่างแม้ตัวเดียว = ปฏิเสธทันที
แก้บล็อกนี้ได้ทางเดียวคือผ่าน serial console

**ขั้นตอนการเสนอแก้**

1. agent เรียก tool `propose_soul_edit` (แยกจาก `write_file` ซึ่งยัง `deny` กับ `identity/` ตลอด)
   ต้องส่งมาพร้อม: diff, เหตุผล, และสิ่งที่คาดว่าจะเปลี่ยนไปในพฤติกรรม
2. ระบบเขียน proposal ลง `identity/pending/<timestamp>.diff` — **ลงแฟลช ไม่ใช่ RAM** จะได้รอดการรีบูต
3. ส่งเข้า Telegram เป็น diff ที่อ่านง่าย พร้อมปุ่ม อนุมัติ / ปฏิเสธ / ดูเต็ม
   (diff ยาวเกิน 3,500 ตัวอักษรให้ตัดแล้วแนบเป็นไฟล์ — Telegram จำกัดข้อความที่ 4,096)
4. ข้อความต้องแสดง **ระยะห่างสะสมจาก baseline** เสมอ เช่น
   `แก้ครั้งที่ 7 · ต่างจากต้นฉบับสะสม 23 บรรทัด (31%)`
   นี่คือมาตรการหลักที่กัน drift — ทำให้คนเห็นภาพรวมทุกครั้งที่ตัดสินใจ ไม่ใช่เห็นแค่การแก้ครั้งนี้
5. อนุมัติ → snapshot ไฟล์เดิมลง `identity/.soul-history/<timestamp>.md` แล้วเขียนทับแบบ atomic
6. ปฏิเสธหรือครบ 24 ชม. → ลบ proposal และบันทึกเหตุลง journal

### 18.3 ขอบเขตที่บังคับใช้เสมอ

- **ไม่เกิน 1 ครั้งต่อวัน** และไม่เกิน 4 ครั้งต่อเดือน — ทำให้ drift ช้าพอที่คนจะทัน
- diff แก้ได้ไม่เกิน 20% ของไฟล์ต่อครั้ง เกินกว่านั้นให้ปฏิเสธและบอกให้ซอยย่อย
- เก็บ history 20 เวอร์ชัน + **เก็บ `SOUL.baseline.md` ไว้ถาวรไม่มีวันลบ**
- คำสั่ง `/soul` = ดูไฟล์ปัจจุบัน, `/soul diff` = เทียบกับ baseline, `/soul revert [n]` = ย้อนกลับ
- ทุกการแก้ที่สำเร็จบันทึกลง `memory/journal/` เป็น audit trail
- ระหว่างมี proposal ค้าง ห้ามเสนอเพิ่ม

### 18.4 สิ่งที่ยังห้ามเด็ดขาด

agent แก้ `settings.json`, `config/`, allowlist, เพดาน token และ tool policy ไม่ได้ทุกกรณี
ต่อให้ผ่านการอนุมัติก็ตาม — ช่องทางเดียวคือ serial console
เหตุผล: การอนุมัติผ่าน Telegram เป็นการกดปุ่มบนอุปกรณ์ที่อาจถูกยึดหรือถูกหลอกได้
สิ่งที่ควบคุมความปลอดภัยจึงต้องการการเข้าถึงทางกายภาพ

## 19. ระบบเสียง

C5 ทำได้จริง แต่มีข้อจำกัดที่กำหนดรูปแบบการใช้งานทั้งหมด ต้องรู้ก่อนออกแบบฮาร์ดแวร์

### 19.1 ทำไมถึงเป็น push-to-talk

C5 **ไม่รองรับ AFE** ซึ่งรวม AEC (echo cancellation), NS และ BSS — รองรับเฉพาะ ESP32, S3, P4 และ S31
แปลว่าถ้าไมค์เปิดขณะลำโพงพูด มันจะได้ยินเสียงตัวเองโดยไม่มีอะไรมาหักล้าง

<cite index="42-1">WakeNet9s รองรับ C5 ได้ เพราะออกแบบมาสำหรับชิปที่ไม่มี PSRAM และไม่รองรับ SIMD</cite>
แต่ wake word บนเครื่องที่ไม่มี AEC ให้ประสบการณ์ครึ่ง ๆ กลาง ๆ: เรียกได้ แต่ขัดจังหวะไม่ได้
ซึ่งเป็นสิ่งที่คนคาดหวังจากอุปกรณ์สั่งงานด้วยเสียงเป็นอย่างแรก

**Kaam จึงใช้ปุ่มอย่างเดียว ไม่มี wake word** — และปุ่มไม่ใช่การยอมแพ้ แต่แก้ปัญหาได้ตรงกว่า:

| เรื่อง | ปุ่มให้อะไร |
|---|---|
| ไม่มี AEC | ไม่เป็นปัญหาเลย เพราะไมค์กับลำโพงไม่เคยทำงานพร้อมกัน |
| ขัดจังหวะ (barge-in) | กดปุ่ม = หยุดเสียงทันที แล้วพูดใหม่ได้ — ได้ผลเหมือน barge-in โดยไม่ต้องใช้ DSP |
| ความเป็นส่วนตัว | ไมค์ไม่เคยเปิดค้าง I2S clock ไม่เดินจนกว่าจะกด พิสูจน์ได้ด้วยตาจาก LED |
| SRAM | คืนมา ~40 KB ทำให้ headroom กลับไปอยู่ในเกณฑ์ปลอดภัย |
| แฟลช | ไม่ต้องมี partition สำหรับโมเดล WakeNet |
| ความซับซ้อน | ตัด dependency `esp-sr` ออกทั้งก้อน |
| การรู้ว่าเมื่อไหร่พูดจบ | ปล่อยปุ่ม = จบ ไม่ต้องมี VAD เลย |

ข้อแลกเปลี่ยนเดียวคือต้องเอื้อมมือไปแตะเครื่อง ซึ่งกับอุปกรณ์ที่วางบนโต๊ะทำงานถือว่ายอมรับได้
และถ้าวันหนึ่งอยากได้ wake word จริง ๆ นั่นคือเหตุผลให้ข้ามไป P4 ซึ่งเป็นคนละเครื่อง

### 19.2 ฮาร์ดแวร์ (เป็นตัวเลือกเสริม ไม่ใช่ของบังคับ)

| ส่วน | ชิ้นส่วน | หมายเหตุ |
|---|---|---|
| **ปุ่ม** | tactile หนึ่งตัว ต่อ GPIO แบบ pull-up | หัวใจของระบบ ใช้ยืนยัน tool ได้ด้วย |
| ไมค์ | I2S MEMS เช่น ICS-43434 หรือ INMP441 | 16 kHz mono |
| ลำโพง | MAX98357A (I2S DAC + amp คลาส D) | ขับลำโพง 4–8Ω ตรง ๆ |
| ไฟบอกสถานะ | WS2812 หนึ่งดวง | ฟัง / คิด / พูด / ผิดพลาด |

ถ้าออกแบบ PCB เอง แนะนำให้ปุ่มควบคุมไฟเลี้ยงไมค์ผ่าน MOSFET ด้วย —
ทำให้ "ไมค์ปิดอยู่" เป็นข้อเท็จจริงทางไฟฟ้าที่วัดได้ ไม่ใช่แค่คำสัญญาของเฟิร์มแวร์

ต้องออกแบบให้ **บอร์ดที่ไม่มีอุปกรณ์เสียงยังทำงานได้ครบทุกอย่างผ่าน Telegram**
เสียงเป็น feature flag ตอน compile ไม่ใช่สมมติฐานของสถาปัตยกรรม

### 19.3 พฤติกรรมของปุ่ม

| การกด | ผล |
|---|---|
| กดค้าง | อัดเสียง (LED ฟ้า) — stream ขึ้น STT ระหว่างที่ยังกดอยู่ |
| ปล่อย | ปิดการอัด ส่งท้าย แล้วเริ่มเทิร์น |
| กดค้าง < 300 ms | ถือว่าเผลอกด ยกเลิก ไม่ส่งอะไร |
| แตะสั้นขณะกำลังพูด | **หยุดเสียงทันที** ล้าง ring buffer (นี่คือ barge-in) |
| แตะสั้นขณะกำลังคิด | ยกเลิกเทิร์น |
| กดค้าง 5 วินาทีตอน idle | เข้าโหมด provisioning ผ่าน serial |

debounce 20 ms ในซอฟต์แวร์ อ่านผ่าน GPIO interrupt ไม่ต้อง poll

### 19.4 สายการทำงาน

```
[กดปุ่มค้าง]
        │
        ▼
   I2S เปิด ──▶ 16 kHz PCM ──▶ stream ขึ้น STT ทันที (chunked upload)
        │                          ระหว่างที่ยังกดอยู่
        ▼
   [ปล่อยปุ่ม] ──▶ ปิด I2S ──▶ ส่ง chunk สุดท้าย
        │
        ▼
   ข้อความ ──▶ inbox_q  ◀── เข้า code path เดียวกับ Telegram ทุกประการ
        │
        ▼
   agent turn ──▶ ตัดตามขอบประโยค
        │
        ▼
   TTS API (ขอ PCM ตรง ๆ) ──▶ ring buffer ──▶ I2S ──▶ ลำโพง
                                    ▲
                            [แตะปุ่ม] ──▶ ล้าง buffer หยุดทันที
```

จุดที่ง่ายลงอย่างมีนัยสำคัญเมื่อเทียบกับแบบมี wake word: **ไม่มี VAD ไม่มี state machine ของการตื่น**
ปุ่มบอกจุดเริ่มและจุดจบอย่างชัดเจน ซึ่งแม่นกว่าอัลกอริทึมใด ๆ และไม่มีทาง false positive

### 19.5 การตัดสินใจเชิงเทคนิค

**ขอ PCM จาก TTS ไม่ขอ MP3** — OpenAI TTS ส่ง PCM ดิบได้ ป้อนเข้า I2S ได้ตรง
ไม่ต้อง decode MP3 ซึ่งจะกิน CPU ที่ต้องแบ่งกับ TLS อยู่แล้วบนคอร์เดียว
แลกด้วยแบนด์วิดท์ที่สูงกว่า ซึ่งบน WiFi 6 ไม่ใช่ปัญหา

**ตัด TTS ตามขอบประโยค** — ไม่รอ LLM พูดจบทั้งย่อหน้า พอเจอ `.` `?` `!` หรือ `ๆ` ที่จบประโยค
ให้ยิง TTS ประโยคนั้นทันที ลด time-to-first-audio จาก ~8 วินาทีเหลือ ~2.5 วินาที
นี่คือความต่างระหว่าง "ใช้ได้" กับ "ทนไม่ไหว"

**ไม่เก็บไฟล์เสียงลงแฟลช** — stream ขึ้น STT ระหว่างที่ยังอัดอยู่
เสียง 10 วินาทีเท่ากับ 320 KB ซึ่งไม่ควรค้างใน PSRAM โดยไม่จำเป็น
ผลพลอยได้คือความเป็นส่วนตัว: ไม่มีเสียงหลงเหลือในเครื่อง

**Ring buffer ขาเล่น 128 KB ใน PSRAM** — บนคอร์เดียวที่ต้องถอดรหัส TLS ไปด้วย
buffer เล็กกว่านี้จะทำให้เสียงสะดุดตอน handshake
และเพราะ buffer ใหญ่ การ "หยุดพูด" จึงต้องล้าง buffer ไม่ใช่แค่หยุดป้อน
ไม่งั้นจะพูดต่ออีกหลายวินาทีหลังผู้ใช้กดหยุด

### 19.6 ผลกระทบต่องบประมาณ

เพิ่มเข้าตาราง §3:

| ผู้ใช้ | SRAM | PSRAM |
|---|---|---|
| I2S DMA buffer (rx + tx) | 16 KB | — |
| Ring buffer ขาเล่น | — | 128 KB |
| STT staging | — | 64 KB |
| Task `audio_in` / `audio_out` | 12 KB (stack) | — |
| **รวม SRAM ที่เพิ่ม** | **~28 KB** | |

headroom SRAM เหลือประมาณ 70 KB ซึ่งยังสูงกว่าเกณฑ์เตือน 45 KB อย่างสบาย —
ต่างจากกรณีมี wake word ที่จะเหลือราว 30 KB และต้องมีกลไกโหลด/ปล่อยโมเดลมาแก้

**RAM ขาเข้าน้อยมากเพราะไม่เก็บไฟล์เสียง** — stream ขึ้น STT ระหว่างที่ยังกดปุ่มอยู่
เสียง 10 วินาทีเท่ากับ 320 KB ซึ่งไม่เคยอยู่ในเครื่องพร้อมกันทั้งก้อน
ผลพลอยได้คือความเป็นส่วนตัว: ไม่มีเสียงหลงเหลือในแฟลชเลย

### 19.7 ต้นทุนที่ต้องยอมรับ

- ค่าใช้จ่ายเพิ่มขึ้นมาก — STT + LLM + TTS ต่อหนึ่งเทิร์น ควรมีเพดานรายวันแยกสำหรับเสียง
- กำลังไฟจาก ~0.5 W เป็น ~1.2 W ตอนเล่นเสียง — USB ยังเอาอยู่แต่ต้องเผื่อ
- หน่วงรวมประมาณ 2.5–4 วินาทีต่อการตอบหนึ่งครั้ง
